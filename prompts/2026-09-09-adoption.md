## Règles dures — les enfreindre annule la nuit

- **Branche unique** : `feat/adoption-blockers`, créée depuis `main` à la
  première itération. Tout le travail y va.
- **Jamais `git push`.** Jamais `gh pr create`. La revue se fait en local demain.
- **Jamais de déploiement** : ne lance pas `scripts/deploy.sh`, ne touche pas à
  `docker-compose.prod.yml`, `Caddyfile`, `.env`, ni à quoi que ce soit qui
  parle à la production. La base de production ne doit jamais être atteinte.
- **Une migration Alembic est autorisée** si #21 en a besoin (version des
  conditions acceptées). Génère la révision, vérifie `upgrade` **et**
  `downgrade` sur une base locale, jamais ailleurs.
- **Un commit par issue**, message en français, format `feat(...)` / `fix(...)`
  comme l'historique, avec `Closes #<n>` en pied. Pas de commit fourre-tout.
- **Ne touche pas au contenu pédagogique** (`backend/scripts/seed_*.py`) :
  #23 se règle en masquant les niveaux sans pack publié, pas en semant.
- **Ne modifie pas `progress-adoption.txt` autrement que pour y écrire ton
  avancement** (voir plus bas).

## Vérifications obligatoires avant chaque commit

```bash
cd backend && uv run ruff check app/ && uv run ruff format --check app/ && uv run mypy app/ && uv run pytest -q
cd ../frontend && pnpm lint && pnpm exec tsc --noEmit
```

Les tests backend tournent sur SQLite en mémoire (`backend/tests/conftest.py`),
donc aucune base externe n'est nécessaire. **Un commit dont les vérifications
ne passent pas est un échec** : corrige, ou reviens en arrière sur ce fichier.

Chaque issue doit apporter au moins **un test qui échoue sans le correctif** —
pas un test qui vérifie du plomberie, un test qui vérifie ce qu'un parent
observe. Si tu ne vois pas quoi tester, dis-le dans le journal plutôt que
d'écrire un test décoratif.

## Conventions du dépôt

`CLAUDE.md` fait loi : `uv` côté backend (jamais pip), `pnpm` côté frontend, et
le client API est **généré par Orval** — si tu changes un schéma backend,
régénère le client au lieu d'écrire du type à la main.

Le français est la langue de l'interface et des messages d'erreur destinés aux
parents. Les docstrings suivent le style existant du module que tu touches.

## Journal — `progress-adoption.txt`

À chaque itération, ajoute une section datée avec : l'issue traitée, ce qui a
été fait, le résultat exact des vérifications, et ce qui reste.

Quand les quatre issues sont livrées et vérifiées, écris en tête du fichier :

```
## Current State: COMPLETED
```

Si tu es bloqué — décision produit à prendre, dépendance manquante, test
impossible à écrire honnêtement — écris :

```
## Current State: BLOCKED
```

suivi de la question exacte à poser à Arnaud. **Un `BLOCKED` explicite vaut
mieux qu'un contournement silencieux.** C'est la sortie honorable, pas un échec.
